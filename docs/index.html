Lesson 1Why P existsdone

The problem. Distributed systems fail because of interleavings, not bad logic. Your coordinator sends a commit, a replica dies mid-write, a retry arrives out of order. Tests catch maybe one of these orderings. There are millions.

P's answer. Write a model of your system as communicating state machines. Then a checker explores the interleavings systematically — every order in which the machines can take their steps — looking for a scenario that violates a property you stated. Lost messages and crashed machines are part of that search too, once you model them (Lesson 4); P's send itself is reliable. When it finds one, it hands you the exact sequence of steps.

Three concepts, and that's really most of it:

ConceptWhat it is
event A typed message. event ePing : machine; means "a ping carrying a machine reference."
machine A state machine with local variables and an input queue. It's in exactly one state; it handles events, updates variables, and moves via goto.
spec An observer machine that watches events and asserts invariants. Specs never send messages; they only judge.

The mental shift from testing

You don't write "given input X, expect output Y." You write "no matter what happens, two clients must never hold the lock at once" — and let the checker hunt for the counterexample.

Installing (Windows / PowerShell)

P needs .NET SDK 8.0 specifically, plus Java 11+.

winget install Microsoft.DotNet.SDK.8
winget install Microsoft.OpenJDK.17

# close and reopen PowerShell so PATH updates, then:
dotnet --list-sdks     # need an 8.0.*
java -version          # need 11+

Then the P tool itself. If your machine has no NuGet feed configured, the install fails with No NuGet sources are defined or enabled — add the default feed first:

dotnet nuget add source https://api.nuget.org/v3/index.json -n nuget.org
dotnet tool install --global P

# verify (PowerShell has no `which`)
Get-Command p
p --version

If p isn't recognized, add %USERPROFILE%\.dotnet\tools to your PATH and restart the shell. Editor: VS Code plus the Peasy extension —

winget install Microsoft.VisualStudioCode
code --install-extension PLanguage.peasy-extension

Lesson 2Your first P programdone

A client pings a server, the server pongs back. Save as ClientServer.p:

event ePing : machine;   // payload: who to reply to
event ePong;             // no payload

machine Client {
  var server : machine;

  start state Init {
    entry (s : machine) {      // payload passed at creation
      server = s;
      send server, ePing, this;
      goto WaitingForPong;
    }
  }

  state WaitingForPong {
    on ePong goto Done;
  }

  state Done {
    entry { print "client got pong"; }
  }
}

machine Server {
  start state Listening {
    on ePing do (client : machine) {
      send client, ePong;
    }
  }
}

machine Main {
  start state Init {
    entry {
      var server : machine;
      server = new Server();
      new Client(server);
    }
  }
}

test tcSingleClient [main = Main]: { Main, Client, Server };
p compile
p check -tc tcSingleClient -i 100

What each piece is doing

  • send is asynchronous and non-blocking — it puts the event in the target's input queue and returns immediately. Each queue is FIFO, so two events one machine sends to another arrive in the order sent. What the checker varies is which machine runs next, so events from different senders can reach a queue in any order — that's the whole point.
  • on ePing do (client : machine) { ... } is a handler that stays in the current state.
  • on ePong goto Done transitions instead.
  • entry runs once when you arrive in a state.
  • -i 100 means: explore 100 different schedules, each with different interleavings and machine orderings.

Read the output carefully

All 100 schedules pass, and the summary says "Explored 1 timeline." One client, one server, nothing to reorder — only one distinct behavior exists. The checker had nothing to do, because we never told it what "correct" means. That's Lesson 3.

Lesson 3Specs, and a bug worth findingcurrent

Two clients, one lock server, and a server that grants the lock to anyone who asks. Save as LockServer.p in the same folder — p compile picks up every .p file there, which is why the driver below is named LockDriver rather than Main: machine names must be unique across the project.

event eAcquire : machine;
event eRelease : machine;
event eGranted : machine;

machine LockClient {
  var server : machine;

  start state Init {
    entry (s : machine) {
      server = s;
      send server, eAcquire, this;
      goto WaitingForLock;
    }
  }

  state WaitingForLock {
    on eGranted goto InCriticalSection;
  }

  state InCriticalSection {
    entry {
      send server, eRelease, this;
      goto Done;
    }
  }

  state Done { }
}

machine LockServer {
  start state WaitForRequests {
    on eAcquire do (client : machine) {
      send client, eGranted, client;      // BUG: grants to anyone who asks
    }
    on eRelease do (client : machine) { }
  }
}

spec MutualExclusion observes eGranted, eRelease {
  var holder : machine;
  var locked : bool;

  start state Init {
    on eGranted do (client : machine) {
      assert !locked,
        format("lock granted to {0} while {1} still holds it", client, holder);
      locked = true;
      holder = client;
    }
    on eRelease do (client : machine) {
      locked = false;
    }
  }
}

machine LockDriver {
  start state Init {
    entry {
      var server : machine;
      server = new LockServer();
      new LockClient(server);
      new LockClient(server);
    }
  }
}

test tcMutualExclusion [main = LockDriver]:
  assert MutualExclusion in { LockDriver, LockClient, LockServer };

The one new idea: spec

A spec machine can't send, can't new, can't use this, and exactly one instance exists globally. It runs synchronously: the moment any machine executes send client, eGranted, ..., the spec's handler fires before anything else happens. So it sees a true global ordering of the events it observes — something no real participant in a distributed system could.

Don't forget to wire it up

assert MutualExclusion in { ... } in the test declaration is what attaches the spec. Without that line, the spec is dead code and the test passes silently.

p compile
p check -tc tcMutualExclusion -i 100

Question before you run it

The server grants unconditionally — so why might some of the 100 schedules still pass?
